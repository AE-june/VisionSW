## 0. 작업 시작 전 필독

### 이 프로그램의 목적을 잊지 말 것

VisionSW는 **노드 그래프로 검사 레시피를 조립하는 범용 도구**다. 레시피가 프로그램이고 엔진이 인터프리터다.
특정 검사(예: 평면 대비 높이 반복성)는 이 도구로 만든 **하나의 레시피일 뿐 목적이 아니다.** 회귀검증에 그 레시피를 쓰는 이유는 σ 0.0015mm라는 알려진 기댓값이 있어 테스트 픽스처로 편하기 때문이다.

따라서 이 문서의 판단 기준은 **"이 검사가 되나"가 아니라 "임의의 검사를 조립할 수 있나"**다.

### 이 문서의 범위

| 파트 | 항목 | 내용 |
|---|---|---|
| **Part A** | **T0-7 (신규)** | 포트별 입력 전달 — 같은 타입 입력 2개 이상을 구분 가능하게. 막혀 있던 `SurfaceSubtract` 완결 |
| **Part B** | **T1-1** | `Profile` 1급 타입 + `ExtractProfile` (높이맵 → 단면) |
| **Part B** | **T1-2** | `ProfileFeature` (단면 → 특징점·측정값) |

**범위 밖**: T1-3 검출점 기하 피팅 · T1-4 Line/Circle 타입 · T1-5 기하 연산 · T2 객체분할 · T3 Fixture/정렬 · T0-6 중첩 ToolBlock · A1~A3 리팩토링.

**T1-3을 뺀 이유**: 검출점을 직선·원으로 피팅하려면 `Line`/`Circle` geometry 타입이 필요하고, 그건 ARCHITECTURE_DIRECTION의 B4(Geometry 1급화)다. 타입 도입이 별도 결정 사항이므로 다음 문서로 분리한다. **Part B만으로도 "단면 뽑고 → 엣지 찾고 → 위치·높이 측정"이 완결**되어 실사용 가치가 있다.

### 절대 원칙 — 기존 동작 보존

**기존 레시피 측정 결과가 bit-identical해야 한다.** 반복성 σ 0.0015mm 수준을 다루므로 부동소수 오차도 회귀로 취급한다.

**Part A는 기존 실행 경로를 건드리므로 이 문서에서 가장 위험한 작업이다.** Part B는 신규 노드 추가라 원칙적으로 기존 레시피에 영향이 없다.

## 1. 현재 코드 사실

추측 아님. 2026-08-03 실측이다. 변경 전 재확인할 것.

### 1.1 입력 병합 — Part A가 고칠 지점

`VisionEngine/src/main.cpp` L190~249. 실행기는 **노드별 스레드**(`std::async` + promise/future)로 병렬이다.

```cpp
// 1. 상류 입력 대기 — dstPort로 정렬은 하지만 라우팅에는 안 쓴다
std::vector<InputRef> ordered = inputsFrom.at(nodeId);
std::stable_sort(ordered.begin(), ordered.end(),
    [](const InputRef& a, const InputRef& b){ return a.dstPort < b.dstPort; });
for (const auto& in : ordered) {
    auto nr = nodeFutures.at(in.source).get();
    upstreamResults.push_back({in, nr.data});
}

// 3. 입력 병합 — 슬롯별 first-wins
for (const auto& [in, o] : upstreamResults) {
    if (o->heightmap && !merged->heightmap)             merged->heightmap = o->heightmap;   // ← 포트 무시
    if (o->cloud     && !merged->cloud)                 merged->cloud     = o->cloud;       // ← 포트 무시
    if (!o->regions.empty() && merged->regions.empty()) merged->regions   = o->regions;     // ← 포트 무시
    if (!o->planes.empty()  && merged->planes.empty())  merged->planes    = o->planes;      // ← 포트 무시
    if (o->heights) { /* concat */ }
    if (o->points)  { /* concat */ }
    if (o->origin && !merged->origin) merged->origin = o->origin;
}
```

**핵심 사실**: `InputRef`에 `srcPort`/`dstPort`가 이미 있고 정렬에도 쓰이지만, **병합은 여전히 타입 슬롯 기준 first-wins다.** 같은 타입 입력 2개면 뒤에 온 것이 조용히 버려진다.

이것은 `heightmap`만의 문제가 아니다. `cloud`·`regions`·`planes` 전부 같은 구조다. 즉 **"같은 타입 입력 2개를 받는 노드"라는 부류 전체가 불가능하다.**

### 1.2 `SurfaceSubtract` 보류 기록

`memory/project_deferred_tasks.md`에 이미 남아 있다:

> **Why:** `main.cpp` 입력 병합 로직이 동일 타입 이중 입력(HeightMap A/B)을 포트 인덱스로 구분하지 못함. first-wins 방식이라 포트 1 HeightMap이 조용히 버려짐. 수정 범위가 `VisionData` 구조 변경 + 기존 20개+ 노드 회귀 검증을 요구해 별도 작업으로 처리.
>
> **How to apply:** 1) `VisionData`에 `std::vector<HeightMapPtr> heightmaps` 추가 2) `main.cpp` 병합 루프에서 `dstPort`로 라우팅 3) 기존 단일 포트 소비 노드들은 fallback 4) 전체 회귀 검증 후 SurfaceSubtract 추가

**이 문서 §2에서 그 계획을 더 안전한 안으로 교체한다** (D-1 참조). 판단 근거는 §2.1.

## 2. Part A — T0-7 포트별 입력 전달

### 2.0 왜 필요한가 (범용성 관점)

**"같은 타입 입력 2개"는 범용 검사 툴에서 계속 재발하는 요구다.** 지금 막힌 건 `SurfaceSubtract` 하나지만 대기 중인 것이 더 있다:

| 조합 | 필요한 것 | 벤치마크 근거 |
|---|---|---|
| 두 표면 차분 (마모·도포량·변형) | HeightMap ×2 | §2-B3 Aurora `SubtractSurfaces` |
| 골든 샘플 비교 | HeightMap ×2 | §2-F4 4사 전부 보유 |
| 멀티센서 병합 | HeightMap ×N | §2-B3 Gocator Surface Stitch |
| Region Boolean (∪∩−) | Region ×2 | §4 T2-4 |
| 두 평면 사이 각도·교선 | Plane ×2 | §4 T1-5 |

즉 **노드 하나를 위한 배관 공사가 아니라 부류 전체를 여는 작업**이다. 지금 하는 게 맞다.

### 2.1 설계 — `byPort` 추가 (기존 슬롯 유지)

### D-1 결정 — 두 안 비교

| | **안 1. `byPort` 추가 (권장)** | 안 2. 슬롯 벡터화 (`heightmaps`) |
|---|---|---|
| 방식 | `VisionData`에 `std::vector<VisionDataPtr> byPort` 추가. 병합 시 기존 슬롯 채우기 **+** 포트별 원본을 그대로 보관 | `heightmap`을 `std::vector<HeightMapPtr> heightmaps`로 교체 + 소비자 전원 fallback |
| 기존 노드 영향 | **없음.** 기존 슬롯 로직 무변경 → CSV diff 0이 구조적으로 보장 | 20+ 노드 전부 수정 필요. fallback 실수 시 조용한 오류 |
| 적용 범위 | **모든 타입 동시 해결** (HeightMap·Cloud·Region·Plane) | HeightMap만. Region/Plane은 또 같은 작업 반복 |
| 단점 | 입력 접근 경로가 2개(레거시 슬롯 / `byPort`)로 일시 이원화 | 회귀 위험이 크고 범위가 넓다 |
| 메모리 | `shared_ptr` 복사뿐 (데이터 복제 없음) | 동일 |

**안 1 채택.** `memory/project_deferred_tasks.md`의 계획(안 2)을 교체한다. 근거: 안 2도 결국 fallback으로 이원화를 만들면서(그 메모 3단계) **회귀 위험만 더 크고 타입별로 반복해야 한다.** 안 1은 한 번에 전부 열리고 기존 경로를 건드리지 않는다.

이원화는 의도된 과도기다. 신규 노드는 `byPort`를 쓰고, 레거시 슬롯은 기존 노드가 계속 쓴다. 통합 시점은 §10에 남긴다.

### 2.2 타입

```cpp
// Core/include/VisionData.h
struct VisionData {
    // ... 기존 슬롯 전부 유지 ...

    // T0-7: 포트별 입력. 같은 타입 입력 2개 이상을 구분해야 하는 노드가 쓴다.
    // 인덱스 = 이 노드의 입력 포트 번호(dstPort). 연결 없는 포트는 nullptr.
    // 기존 노드는 이 필드를 무시하고 레거시 슬롯(heightmap/regions/...)을 계속 쓴다.
    std::vector<VisionDataPtr> byPort;

    // 포트 접근 헬퍼 — 범위 밖/미연결이면 nullptr 반환 (호출부에서 분기 없이 쓰게)
    VisionDataPtr port(std::size_t i) const {
        return i < byPort.size() ? byPort[i] : nullptr;
    }
    HeightMapPtr portHeightMap(std::size_t i) const {
        auto p = port(i);
        return p ? p->heightmap : nullptr;
    }
};
```

**규약**
- `byPort`의 인덱스는 **`dstPort` 그대로**다. 포트 0·2만 연결됐으면 `byPort = {p0, nullptr, p2}` (size 3).
- 같은 `dstPort`에 엣지 2개가 오면 **첫 번째(정렬 후)만 `byPort`에 넣는다.** 그 경우도 레거시 concat 동작은 유지된다(`heights`/`points`).
- `byPort[i]`는 **상류 노드의 출력 원본 포인터**다. 복사하지 않는다. 읽기 전용으로 취급하고 **절대 수정하지 말 것** — 병렬 실행에서 다른 노드가 같은 포인터를 본다.

### 2.3 병합 루프 변경

`main.cpp` L219~249의 병합 루프에 **추가만** 한다. 기존 줄은 손대지 않는다.

```cpp
auto merged = std::make_shared<VisionData>();
merged->frames = runFrames;

// T0-7: 포트별 입력 보관 — 최대 dstPort까지 크기 확보
std::size_t maxPort = 0;
for (const auto& [in, o] : upstreamResults) maxPort = std::max(maxPort, (std::size_t)in.dstPort);
merged->byPort.assign(maxPort + 1, nullptr);

bool any = false;
for (const auto& [in, o] : upstreamResults) {
    if (!o) continue;
    VISION_LOG_INFO("[pipeline] edge {}:{} -> {}:{}", in.source, in.srcPort, nodeId, in.dstPort);
    any = true;

    // T0-7: 포트별 보관 (같은 포트 중복 시 첫 번째 유지)
    if (!merged->byPort[in.dstPort]) merged->byPort[in.dstPort] = o;

    // ── 이하 기존 레거시 병합. 한 줄도 바꾸지 않는다 ──
    if (o->heightmap && !merged->heightmap) merged->heightmap = o->heightmap;
    // ...
}
```

**주의**: `upstreamResults`가 비어 있으면 `inputData`가 `nullptr`이다(기존 동작). 그 경로를 바꾸지 말 것.

### 2.4 `SurfaceSubtract` 구현

```
입력  : HeightMap (포트 0 = A), HeightMap (포트 1 = B)
출력  : HeightMap
카테고리: 변환
```

[벤치마크 §2-B3](./3D_BASELINE_BENCHMARK.md). Aurora `SubtractSurfaces`. **골든 비교(§2-F4)의 최소 구현**이기도 하다.

**입력 획득**: `input->portHeightMap(0)`, `input->portHeightMap(1)`. **레거시 `input->heightmap`을 쓰지 말 것** — 그게 이 노드가 막혔던 원인이다.

**파라미터**

| 이름 | 기본 | 의미 |
|---|---|---|
| `absolute` | `false` | true면 \|A−B\| |
| `nanPolicy` | `"propagate"` | `propagate`(어느 한쪽 NaN → NaN) \| `zero`(NaN을 0으로 간주) |

**규약**
- 포트 0 또는 1이 비었으면 `Fail` + "포트 A/B 모두 연결 필요" 메시지.
- `width`/`height` 불일치 → `Fail`. **조용한 보간 금지.** 리샘플은 사용자가 `SurfaceResample`을 명시적으로 넣는다.
- `xResMm`/`yResMm`/`zResMm` 불일치 → `Fail`.
- `frameId` 불일치(둘 다 비어있지 않고 다름) → `Fail` + `TODO(T0-1 P3)` 주석. `LevelTool`의 방식과 동일하게.
- 출력 `frameId` = A의 `frameId`. 새 프레임 아님, `definedFrames` 비움.
- **Z 인코딩은 `Level`이 확정한 D-1 B안을 따른다**: 출력 `zZeroCount = 0`, `zResMm`은 A와 동일. 차분 결과가 0 근처이므로 float 정밀도가 최대가 된다.
- 채널: 채널0만 차분. 나머지 채널은 A에서 복사, `channelRoles` 보존. (`Level`과 동일 규약)

**성능**: 34M px 선형 패스. `Level`과 같이 **직렬로 먼저 구현하고 실측**한다. `perf_findings.md`의 메모리 대역폭 교훈 — 선형 패스 병렬화는 역효과였다.

## 3. Part B — T1-1 Profile · T1-2 특징점 검출

### 3.0 왜 이게 최대 공백인가

[벤치마크 §2-D](./3D_BASELINE_BENCHMARK.md) — 조사한 5개 제품 중 **4개가 보유**하고 VisionSW만 0개다. 미보유는 HALCON뿐이고 HALCON은 애초에 높이맵 전용 타입이 없어서다.

| 제품 | 보유 형태 |
|---|---|
| Aurora | `1D Edge Detection 3D` 9필터 + `Shape Fitting 3D` 10필터 + `SurfaceProfileAlongPath` 등 4개 = **19+** |
| Gocator | Surface Section → Profile 툴 14개 + Feature Point **14종**(Max Z, Min Z, Min X, Max X, Average, Corner, Top/Bottom/Left/Right Corner, Rising Edge, Falling Edge, Any Edge, Median) |
| InsWorks | 3D 횡단면 툴 1개에 통합 (컨투어 획득 → 특징 추출 → 측정) |
| eVision | ZMap 자체가 정사영이므로 2D 게이지(EasyGauge) 재사용 |

**"높이맵을 1급으로 다루는 제품은 예외 없이 이 캘리퍼를 갖는다."** 3D 측정의 대부분이 결국 "단면에서 재는" 일이기 때문이다.

### D-2 결정 — 프리미티브 분해형 vs 통합 툴형

벤치마크가 두 설계 선택지를 드러냈다:

| | 분해형 (Aurora) | 통합형 (InsWorks) | 중간 (Gocator) |
|---|---|---|---|
| 구성 | 추출·검출·피팅을 19개 독립 필터로 | 단일 "3D 횡단면 툴" 하나 | 툴 1개 + Feature Point를 파라미터 14종으로 |
| 장점 | 조합 자유도 최대 | 노드 수 최소, 배우기 쉬움 | 균형 |
| 단점 | 노드 폭발, 팔레트 비대 | 조합 불가, 툴 안에 로직 갇힘 | — |

**Gocator식 중간안 채택.** 노드는 2개(`ExtractProfile`, `ProfileFeature`)만 만들고, **특징 종류는 `kind` 파라미터로 열거**한다.

근거: (1) 1인 프로젝트에서 노드 19개는 유지 비용이 크다 (2) 그러면서도 `Profile`이 포트로 흐르므로 추출과 검출을 자유롭게 재조합할 수 있다 — 통합형의 조합 불가 문제를 피한다 (3) `HeightMeasure`가 이미 집계를 파라미터(`Mean`/`Max`/`HighTail`)로 열거하는 관례와 일관된다.

### 3.1 `Profile` 타입

```cpp
// Core/include/Profile.h  (신규)
#pragma once
#include <vector>
#include <string>
#include <memory>

namespace vision {

// ─────────────────────────────────────────────────────────────────
//  Profile — 1D 샘플 신호 (높이맵 단면). 1급 iconic 타입.
//
//  SoA 배치: 같은 인덱스 i가 한 샘플. 캐시 효율 + 부분 접근 용이.
//    s[i]  경로 시작점부터의 호장(arc length), mm. 단조 증가.
//    x[i], y[i]  샘플 위치, 소속 프레임의 mm 좌표.
//    z[i]  샘플 높이, mm. NaN = 무효 (원본 무효 픽셀 또는 경로가 격자 밖).
//
//  z는 mm로 저장한다 — HeightMap의 raw count 인코딩을 쓰지 않는다.
//  이유: Profile은 격자가 아니라 신호이므로 분해능·zZeroCount 개념이
//  불필요하고, 소비자(특징 검출·측정)가 전부 mm를 원한다.
// ─────────────────────────────────────────────────────────────────
struct Profile {
    std::vector<double> s;
    std::vector<double> x, y, z;
    std::string frameId;    // 이 Profile의 좌표가 유효한 프레임. "" = 미지정
    std::string label;      // 다중 추출 시 식별용 (예: "row:120")

    std::size_t size() const { return z.size(); }
    bool empty()       const { return z.empty(); }
    bool valid(std::size_t i) const { return i < z.size() && !std::isnan(z[i]); }
};

using ProfilePtr = std::shared_ptr<Profile>;

} // namespace vision
```

**`VisionData`에 추가** — `regions`/`planes`와 동일하게 **처음부터 벡터**로 둔다. 다중 단면 추출이 벤치마크 공통 기능이고(Aurora `SurfaceMultipleProfilesAlongAxis`), 나중에 벡터화하는 비용을 피한다.

```cpp
std::vector<ProfilePtr> profiles;

const ProfilePtr& profile0() const { /* regions0/plane0과 동일 패턴 */ }
void setProfile(ProfilePtr p)      { profiles.clear(); if (p) profiles.push_back(std::move(p)); }
bool hasProfile() const { return !profiles.empty() && profiles.front() && !profiles.front()->empty(); }
```

**UI PortType 추가**: `'Profile'`. `PORT_COLORS`에 색 하나 배정 (기존 7색과 구분되는 것).

**프레임**: Profile은 **새 프레임을 만들지 않는다.** 소스 HeightMap의 `frameId`를 그대로 복사한다. 격자가 아니라 그 프레임 안의 경로일 뿐이다.

### 3.2 `ExtractProfile` — 높이맵 → 단면

```
입력  : HeightMap, Region (선택)
출력  : Profile (배열 가능)
카테고리: 변환
```

**파라미터**

| 이름 | 기본 | 의미 |
|---|---|---|
| `mode` | `"line"` | `line` \| `axisX` \| `axisY` |
| `p0` / `p1` | `{0,0}` | `mode=line`. 경로 양 끝점. 단위는 `unit` |
| `unit` | `"px"` | `px` \| `mm` — 좌표 해석 단위 |
| `count` | `0` | `mode=line` 샘플 수. 0이면 경로 길이 기준 1px 간격 자동 |
| `interp` | `"bilinear"` | `nearest` \| `bilinear` — 격자 사이 보간 |
| `index` | `0` | `mode=axisX/Y`. 단일 행/열 인덱스 |
| `span` | `1` | `mode=axisX/Y`. 이웃 N줄을 평균 (노이즈 저감). 1이면 단일 |
| `repeat` | `1` | `mode=axisX/Y`. N개 평행 단면을 균등 간격으로 뽑아 `profiles` 배열 출력 |
| `channel` | `0` | 어느 채널을 z로 쓸지 |

**모드별 동작**

- **`line`**: `p0`→`p1` 직선을 `count`개로 균등 샘플. 격자 사이는 `interp`로 보간. 경로가 격자 밖이면 그 샘플 `z = NaN`.
- **`axisX`**: `index` 행을 그대로 뽑는다(보간 없음, 원본 값 보존). `span>1`이면 이웃 행의 유효 픽셀만 평균.
- **`axisY`**: `index` 열. 동일.

**`axisX/Y`에 보간이 없는 게 중요하다.** 측정 경로에서 원본 값을 그대로 쓸 수 있는 통로를 남겨둔다. `line` 모드는 임의 각도라 보간이 불가피하다.

**규약**
- Region 입력이 있으면 **Region 밖 샘플은 `z = NaN`**으로 만든다 (경로를 자르지 않는다 — 인덱스가 유지되어야 다운스트림이 위치를 안다).
- 출력 `Profile::frameId` = 입력 HeightMap의 `frameId`.
- `x`/`y`는 **항상 mm**로 채운다 (`xMm()`/`yMm()` 사용). `unit=px`는 파라미터 해석에만 쓴다.
- `s[0] = 0`, 단조 증가. `axisX`의 경우 `s[i] = xMm(i) - xMm(0)`.
- `repeat > 1`이면 `profiles`에 순서대로 넣는다. **순서는 `index` 오름차순 고정** (결정론).

**결정론**: 샘플 위치 계산에 누적 덧셈을 쓰지 말고 `i/(count-1)` 비율로 매번 계산한다. 누적은 부동소수 오차가 쌓여 재현성이 깨진다.

### 3.3 `ProfileFeature` — 단면 → 특징점·측정값

```
입력  : Profile
출력  : Point, Heights
카테고리: 측정
```

Gocator Feature Point 14종에 대응하는 `kind` 열거형이 이 노드의 본체다.

**파라미터**

| 이름 | 기본 | 의미 |
|---|---|---|
| `kind` | `"maxZ"` | 아래 표 |
| `edgeDir` | `"any"` | `rising` \| `falling` \| `any` — 엣지 계열에서만 |
| `edgeThresholdMm` | `0.05` | 엣지로 인정할 최소 Z 변화량 |
| `smoothWindow` | `3` | 검출 전 이동평균 창 크기(샘플). 1이면 없음 |
| `nth` | `0` | 조건을 만족하는 것 중 몇 번째(0-based). 음수면 뒤에서부터 |
| `searchFromMm` / `searchToMm` | `0` / `0` | 검색 구간 `s` 범위. 둘 다 0이면 전체 |

**`kind` 목록 (Gocator Feature Point 대응)**

| `kind` | 뜻 |
|---|---|
| `maxZ` / `minZ` | 최대/최소 높이 샘플 |
| `maxS` / `minS` | 유효 샘플 중 s가 가장 큰/작은 것 (= 양 끝) |
| `mean` / `median` | 유효 z의 평균/중앙값. 위치는 무게중심 |
| `edge` | `edgeDir`·`edgeThresholdMm` 기준 계단. `nth`로 선택 |
| `ridge` | 국소 볼록 정점 (좌우보다 높음) |
| `valley` | 국소 오목 저점 |
| `corner` | 기울기가 급변하는 점 (2차 차분 최대) |

**출력**
- `Point` — 찾은 위치. `RefPoint`에 `cxMm`/`cyMm`(mm)과 `cx`/`cy`(px 환산) 모두 채운다. **기존 `RefPoint`의 px/mm 이중 보유 구조를 그대로 따른다** — 단일화는 T0-1 Phase 3 범위이고 여기서 건드리지 않는다.
- `Heights` — 그 지점의 z(mm). 후속 `CsvWriter`로 바로 흐른다.
- 못 찾으면 `ToolStatus::Fail` + 이유. **빈 결과를 Ok로 내지 말 것.**

**서브픽셀**: 엣지·리지·코너는 **인접 3점 포물선 피팅으로 서브픽셀 위치**를 낸다. 정수 인덱스만 내면 반복성이 격자 분해능에 갇힌다. 이 프로젝트는 σ 0.0015mm를 다루므로 서브픽셀이 필수다.

**NaN 처리**: 무효 샘플은 검출에서 제외한다. **무효 구간을 건너뛰며 이어붙이지 말 것** — 없는 엣지를 만들어낸다. 무효를 만나면 그 지점에서 연속 구간이 끊긴 것으로 취급한다.

**프레임**: 입력 Profile의 `frameId`를 `RefPoint`가 속한 프레임으로 간주한다. `Profile`이 프레임을 안 만드므로 검사할 게 없다.

### 3.4 UI — Profile 결과 표시

`NodePanel`에 **1D 플롯**이 필요하다. 없으면 사용자가 파라미터를 맞출 수 없다 — 벤치마크 §2-G3(3D 뷰어)와 같은 이유로, 5사 전부 결과를 눈으로 볼 수단을 제공한다.

**최소 요구**
- x축 = `s`(mm), y축 = `z`(mm). 자동 범위.
- NaN 구간은 선을 끊어 표시 (0으로 잇지 말 것 — 없는 형상으로 보인다).
- `ProfileFeature`가 찾은 위치를 세로선/마커로 오버레이.
- `ExtractProfile`이 뽑은 경로를 `ImageViewer` 위에 선으로 오버레이 (어디를 잘랐는지 봐야 한다).

기존 `ImageViewer`·`RoiCanvas`의 오버레이 방식을 재사용한다. 새 차트 라이브러리를 들이지 말고 canvas/SVG로 직접 그린다 — 의존성 추가 대비 이득이 없다.

## 5. Phase 순서 — 위험도 오름차순

```
Phase 0  현재 상태 확인 + baseline.csv 재생성
         (병렬 실행기 도입 후 기준선이 갱신됐는지 확인)

Phase A1 byPort 추가 — VisionData 필드 + main.cpp 병합 루프 추가만
         ← 기존 경로 무변경. 여기서 CSV diff 0이 안 나오면 즉시 되돌린다
Phase A2 SurfaceSubtract 구현 — byPort의 첫 실전 소비자
Phase B1 Profile 타입 + PortType + UI 1D 플롯 골격
Phase B2 ExtractProfile — axisX/axisY 먼저 (보간 없음, 검증 쉬움)
Phase B3 ExtractProfile — line 모드 + 보간
Phase B4 ProfileFeature — maxZ/minZ/mean/median (극값 계열, 서브픽셀 불필요)
Phase B5 ProfileFeature — edge/ridge/valley/corner (서브픽셀 필요)
```

**왜 이 순서인가**

- **A1이 최우선**: 기존 실행 경로를 건드리는 유일한 작업이다. 다른 것과 섞지 말고 단독으로 검증해야 원인 추적이 된다.
- **A2가 A1의 검증**: `SurfaceSubtract`가 A/B를 올바르게 받으면 `byPort`가 동작한다는 증명이다. 단위 테스트로는 병합 루프를 못 검증한다.
- **B2가 B3보다 먼저**: `axisX/Y`는 보간이 없어 원본 값과 직접 대조할 수 있다. 여기서 좌표·NaN·프레임 규약을 확정하고 `line`이 따른다.
- **B4가 B5보다 먼저**: 극값 계열은 서브픽셀이 없어 정답이 자명하다. 여기서 검색구간·NaN·`nth` 규약을 확정한다.

## 7. 금지 사항

1. **`byPort[i]`를 수정하지 말 것.** 상류 출력 원본 포인터이고 병렬 실행에서 공유된다. 읽기 전용.
2. **레거시 병합 로직을 건드리지 말 것.** `byPort`는 추가만 한다 (§2.3).
3. **`IAlgorithmTool::execute(VisionDataPtr)` 시그니처 변경 금지.**
4. **`--repeat-analyze` 경로 파괴 금지.**
